# v1 API 契约冻结与客户端兼容

## 契约文件

- `packages/contracts/openapi.json`：当前服务必须发布的完整 OpenAPI；运行时结构必须与该文件完全一致。
- `packages/contracts/openapi-baseline.json`：仍受支持的上一代客户端基线；只在上一代客户端支持窗口结束后推进。
- `packages/contracts/compatibility-policy.json`：当前/上一修订号、客户端实际消费的 `operationId` 和弃用登记。

`python tools/api_compatibility.py` 同时在 GitHub Actions、GitLab CI 和 Pytest 中执行。仅更新当前快照不能绕过兼容门禁，因为检查器仍会把它与上一代基线比较。

## 当前兼容矩阵

| 客户端 | 状态 | 当前实际消费范围 | 支持要求 |
|---|---|---|---|
| H5 | 已运行 | 登录/绑定/刷新/注销、项目与上传、页面列表/内容与编辑、任务列表、导出创建/列表和制品下载 | 当前与上一契约修订 |
| 管理后台 | 已运行 | 登录、当前用户、用户列表、审计列表 | 当前与上一契约修订 |
| Android | 身份、拍摄与续传基础 | 验证码申请、注册、登录、刷新、注销、当前用户、项目列表/创建、上传创建/查询、分片写入和上传完成已进入产品链路；页面、任务和导出读取仍仅建模 | 当前与上一契约修订 |
| iOS | 工程骨架 | 尚无已接通 API 操作 | 接通后必须登记 `operationId` |

矩阵只陈述仓库当前证据。Android/iOS 的依赖声明或界面骨架不等于已经验证接口兼容。

Android 续传以服务端 `received_chunks` 为唯一确认依据；本地进度仅用于展示，不能据此跳过服务端未确认的分片。正式路径保持 `/v1/uploads/{id}/chunks/{index}`。

## 自动禁止的破坏性变更

对上一代基线，检查器禁止：

- 删除路径、方法、既有响应状态或响应媒体类型；
- 修改稳定 `operationId`；
- 删除模型或既有字段；
- 新增必填字段、必填参数，或把请求体从可选改为必填；
- 修改字段类型、格式、引用、可空性或既有枚举集合。

允许新增端点和可选响应字段。枚举新增值也可能使原生客户端的穷举解析崩溃，因此默认视为破坏性变更；需要时应先增加可忽略的新字段或升级 API 大版本。

## 弃用规则

`/v1` 操作不能只在文档中写“即将删除”。必须同时：

1. 在 OpenAPI 标记 `deprecated: true`；
2. 在兼容策略登记方法、路径、公告日期、停止支持日期和替代方案；
3. 保留至少 90 天，并覆盖当前与上一客户端两代；
4. 客户端先支持新旧字段，再推进上一代基线，最后才删除旧能力。

当前没有已登记弃用。`X-SmartScan-API-Version: v1` 标识 API 大版本，`X-SmartScan-Contract-Revision` 标识当前契约修订；客户端不得把修订号当作拒绝未知可选字段的理由。

## 变更流程

每个接口 PR 必须先修改实现和测试，生成当前 OpenAPI，再运行兼容检查。若失败，优先改为增量兼容设计；确需破坏兼容时必须先完成客户端双读/双写和弃用窗口，或新建 API 大版本。更新上一代基线是发布决策，不是修复 CI 的手段。
