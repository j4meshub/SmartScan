# 账号合并与冲突处理

`ACC-003` 处理历史上同一已验证手机号形成两个统一用户的场景。自动合并只接受可证明、无歧义的强身份；任何候选、身份、资源或运行状态冲突都会拒绝，不按姓名、掩码手机号或客户端传入的用户 ID 猜测。

## 接口流程

1. 已登录用户为待合并手机号申请 `purpose=account_merge` 的短信挑战。
2. 客户端调用 `POST /v1/auth/account-merges`，提交手机号、挑战 ID、验证码和至少 16 位的幂等键。
3. 服务端使用全部保留的手机号 HMAC 版本查找候选；必须恰好存在两个普通、启用且未删除的账号，并且当前用户是其中之一。
4. 最早创建且未删除的用户作为 canonical user，另一用户作为 source user。
5. 服务端校验身份 Provider 不重叠、上传幂等键不冲突、没有待上传分片或运行中作业。
6. 合并成功后撤销两个账号的全部会话，客户端必须重新登录并以返回的 canonical user ID 重建本地索引。

相同幂等键由 canonical user 在重新登录后重试时返回原合并结果，不重复迁移资源。

## 数据与文件迁移

单一数据库事务迁移 source user 的登录身份、项目、页面、页面结果版本、上传和处理作业归属，并删除重复的 source 已验证手机号。source user 保留为 `deleted` 墓碑，旧 ID 不会分配给其他账号。

页面原图、处理结果和仍有实体的上传分片执行以下安全顺序：

1. 将源文件复制到 canonical user 目录下的随机临时文件。
2. 校验源文件、临时副本及数据库已有 SHA-256；处理结果没有历史摘要时，至少校验源副本一致。
3. 使用同文件系统 `os.replace` 原子落位目标文件。
4. 数据库提交成功后只删除已登记的源文件；删除失败时保留安全副本，不把已完成合并误报为失败。
5. 数据库提交或复制过程中失败时回滚全部归属变更，并逆序删除本次创建的目标副本，源文件保持不动。

不递归删除 source user 目录，避免误删未登记或仍需人工核查的文件。

## 冲突矩阵

| 条件 | 结果 |
|---|---|
| 候选不是恰好两个，或当前用户不在候选中 | `account_merge_conflict` |
| 任一账号不是普通、启用账号 | `account_merge_conflict` |
| 两个账号拥有同一 Provider 类型 | `account_merge_identity_conflict` |
| 上传幂等键在合并后会重复 | `account_merge_upload_conflict` |
| source user 仍有待完成上传 | `account_merge_upload_pending` |
| source user 有 `baseline_processing` / `optional_enhancing` 作业 | `account_merge_job_running` |
| 文件缺失、路径越界、目标冲突或哈希不一致 | 拒绝并回滚 |

上述冲突不得由普通用户绕过；后续 `ADMIN-001` 只提供有审计的人工处理入口，不放宽强身份条件。

## 审计与隐私

`account_merge_audits` 记录旧用户 ID、canonical user ID、发起人、规则、结果、幂等键和资源计数。PostgreSQL 使用触发器禁止更新或删除该表。既有 `audit_logs` 保持原始 actor/target，不改写历史；通过合并审计映射旧 ID 才能同时满足事件真实性与统一账号追踪。

审计不保存验证码、完整手机号、文件内容或密钥。跨用户发起合并不会接收目标用户 ID，失败响应只返回稳定冲突码。

## 迁移与回滚

`20261020_0008` 新增不可变合并审计表及 source/canonical 查询索引。降级到 `0007` 只删除合并审计表，不自动拆分已经完成的账号或搬回文件。

生产回滚前必须暂停合并入口并确认没有在途请求。已经完成的合并只能依据审计记录执行经过人工批准的补偿方案，禁止直接降级数据库来伪造“撤销合并”。
