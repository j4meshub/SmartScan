## D-012：企业微信 POC 与正式登录解耦

- 状态：已确认
- 日期：2026-10-20
- 决策：`POC-001` 只建立默认关闭的真实适配器、开发 Mock、可信身份数据和无副作用的账号决策契约，不提前开放正式 OAuth 回调或修改账号数据库。真实适配器固定企业微信官方 HTTPS API 域名并禁止重定向；Mock 明确标记模拟 assurance 且生产禁用。
- 影响：阶段 0 可以验证可信来源、无手机号和冲突路径；正式会话、统一账号事务、短信绑定和冲突审计仍由后续账号工作包实现，真实租户权限保持人工门禁。

## D-013：H5 相机始终保留系统兜底

- 状态：已确认
- 日期：2026-10-20
- 决策：H5 实时相机使用 `getUserMedia`，可用时优先 `ImageCapture`，否则从 video 帧生成 JPEG；无论能力检测结果如何，都保留 `capture=environment` 的系统相机/文件输入。分片恢复以服务端 `received_chunks` 为事实来源，本地只保存项目 ID 与幂等键。
- 影响：浏览器能力或权限失败不会阻断扫描入口；自动测试可以证明已确认分片不重传，但真实相机质量、企业微信兼容性和 4G/5G 恢复仍需人工验收。

## D-014：透视评估使用真实样本数量与可用率双门禁

- 状态：已确认
- 日期：2026-10-20
- 决策：文档透视风险门禁默认要求至少 `100` 个已授权、已脱敏且具备人工四角标注的正样本，同时透视可用率达到 `95%`。可用样本必须检测成功、归一化角点均方根误差不超过 `0.03`，且输出尺寸有效。合成夹具只验证评估器和门禁逻辑，不能作为真实指标通过证据。
- 影响：评估框架可以在没有真实图片的仓库与 CI 中持续回归，但 `POC-003` 在授权固定数据集完成评估和人工复核前保持“等待人工验收”；未达标时先调整算法或产品范围。

## D-015：基础试卷净化默认不处理黑色笔迹

- 状态：已确认
- 日期：2026-10-20
- 决策：`POC-004` 只自动弱化与印刷保护区没有明显冲突的彩色候选。黑色笔迹、深色彩色候选、疑似覆盖印刷内容和大面积异常均保留；风险超过阈值时整页回退原图。净化只向纸张背景弱化，不使用生成式补字或把图像修补结果解释为原文。
- 影响：本地 POC 可以验证保守路径和失败回退，但不会虚构被黑色笔迹遮挡的印刷内容。黑色笔迹分割、模板回填和生产接入分别留给固定数据集验证后的 `EXAM-002`/`EXAM-003`，真实指标保持人工门禁。

## D-016：双页拆分不使用图片中心作为书脊

- 状态：已确认
- 日期：2026-10-20
- 决策：`POC-005` 必须在书本边界内估计书脊暗谷并验证左右页面覆盖率，不能直接从输入图片中心切半。阅读顺序必须显式传入。书脊或任一侧不可信时返回单张原图；边界去弯曲只有在输出几何分数改善时采用。
- 影响：不居中的书本和不等宽页面可以保留各自宽度，低置信场景不会伪造第二页。当前边界分数不代表文字基线质量，产品化仍需真实书籍固定集、文字几何评分和单侧重拍数据模型。

## D-017：容量门禁必须同时具备真实时长与服务器资源证据

- 状态：已确认
- 日期：2026-10-20
- 决策：`POC-006` 固定使用 8 个书页上传、4 个浏览/下载和 4 个普通扫描会话。少于 30 分钟、没有同窗口服务器资源指标、没有实际下载、存在 OOM/任务缺失/隔离违规或非处理请求 P95 不达标时，自动门禁不得通过。工具默认只允许回环目标，非回环 staging 需要精确主机允许和非生产确认。
- 影响：Mock 和短时本地运行只能验证驱动器，不会被误记为目标容量通过。公司服务器恢复后仍需在可重建 staging 上结合监控、日志、磁盘回收、弱网和 BBR 对照完成人工验收，禁止直接压测生产。

## D-018：统一用户、登录身份与已验证手机号分离

- 状态：已确认
- 日期：2026-10-20
- 决策：`users` 只作为稳定用户主体和数据所有权锚点；`user_identities` 保存 Provider 登录主体及本地凭据；`verified_phones` 保存手机号验证事实。`ACC-001` 采用 expand/migrate，保留旧账号列并双写，不在同一迁移中删除兼容字段。
- 影响：现有用户 ID、角色、会话、项目归属和 `/v1` 用户响应保持不变，登录与手机号冲突判断切换到新结构。超级管理员的 `not-bound` 不会被回填为已验证手机号。手机号密文与密钥轮换、真实短信、企微绑定、冲突合并及旧列 contract 分别留给后续工作包。

## D-019：手机号使用版本化 HMAC 与绑定用户的认证加密

- 状态：已确认
- 日期：2026-10-20
- 决策：精确匹配继续使用 HMAC-SHA-256，但每行记录 Pepper 版本且查重覆盖全部保留版本；可恢复号码使用 AES-256-GCM、每次随机 96 位 nonce，并把用户 ID 和加密密钥 ID作为关联数据。数据库保存密钥 ID，不保存密钥。旧账号无法从 HMAC/掩码还原，迁移只标记为 `unavailable`。
- 影响：轮换时必须先同时配置新旧 Keyring，再分批重加密和重算 HMAC；旧版本只有在数据库、备份与回滚窗口均不再引用后才能移除。真实 Secret 管理和生产轮换演练仍需 staging 人工门禁，短信或企微重新验证由后续工作包提供。

## D-020：验证码使用一次性挑战和数据库限频窗口

- 状态：已确认
- 日期：2026-10-20
- 决策：验证码明文不落库，只保存绑定挑战 ID 的 HMAC；挑战 5 分钟有效、最多 5 次尝试并在注册成功时原子消费。手机号和直接连接 IP 使用独立伪名窗口计数与行锁，不信任客户端转发头。
- 影响：并发申请不能通过“先计数后插入”竞态越过上限；真实代理 IP 只能由后续受控 Nginx 信任配置接入。开发 Mock 不等于真实短信，生产强制禁用。

## D-021：企业微信 Provider 身份优先于手机号变化

- 状态：已确认
- 日期：2026-10-20
- 决策：`corp_id:UserId` 是企业微信长期登录主键；已绑定身份始终回到原用户。可信通讯录手机号只用于首次绑定的唯一候选匹配，无手机号必须走一次性票据加短信挑战，多候选或一用户多企微身份冲突禁止自动处理。
- 影响：成员换号不会迁移数据或夺取另一账号；OAuth state 绑定发起浏览器的短期 HttpOnly Cookie，并在外部请求前一次性消费。真实租户权限和回调域名仍需人工验收，复杂账号合并留给 `ACC-003`。

## D-022：账号合并保留历史审计主体

- 状态：已确认
- 日期：2026-10-20
- 决策：账号合并不修改既有 `audit_logs.actor_user_id` 或 `target_user_id`，而是新增不可变 `account_merge_audits` 保存 source user 到 canonical user 的映射、规则、结果和资源计数。文件采用复制、哈希校验、原子落位、数据库提交后删除源文件的补偿协议。
- 影响：与 v1.4“迁移审计主体”的字面表述不同，但避免伪造历史事件，并与既有追加式审计保护一致。查询历史时需联结合并映射；降级迁移不能撤销已完成合并，生产补偿必须人工批准。

## D-023：设备会话采用短访问令牌与轮换刷新链

- 状态：已确认
- 日期：2026-10-20
- 决策：新客户端提供稳定设备 ID 后获得 15 分钟访问令牌和 30 天单次刷新令牌；刷新令牌重放撤销整个设备令牌族。为保持 `/v1` 增量兼容，未提供设备 ID 的当前 H5 和旧客户端继续获得 24 小时访问令牌，新增响应字段可忽略。
- 影响：客户端应以 Keychain、Keystore 或等价安全存储保存刷新令牌并原子替换；设备名 Header 使用 UTF-8 百分号编码。旧兼容模式在 H5/原生客户端完成刷新支持后再通过独立 contract 阶段收缩，不能直接缩短现有客户端会话。

## D-024：账号删除保留最小墓碑并分阶段擦除文件

- 状态：已确认
- 日期：2026-10-20
- 决策：账号删除申请经短信强验证后立即进入 7 天冷静期并撤销会话；到期清理保留不可登录的最小 `users` 墓碑和追加式审计关联，不保留登录身份或可逆手机号。用户目录先原子移动到隔离区，数据库提交后再擦除；擦除失败保持 `cleanup_pending` 可重试。手机号从实际清理起以版本化 HMAC 隔离 30 天。
- 影响：历史审计主体不会因删除而失去关联，也不会把停用误当成删除。旧 HMAC Pepper 必须至少保留到隔离、备份和回滚窗口结束。数据库降级不能恢复已清理数据；公开 AI URL、导出等未来资源必须显式接入同一清理服务。

## D-025：管理权限按目标角色分层并审计失败动作

- 状态：已确认
- 日期：2026-10-20
- 决策：管理员只能读取和管理普通用户；只有超级管理员可以调整角色或管理其他管理员。管理端删除必须复用账号删除状态机，并记录发起人、来源和原因，禁止直接物理删除。所有已认证的管理失败动作进入追加式审计，超出角色范围与不存在目标统一返回 `404`。
- 影响：现有列表响应保持兼容，只增量增加过滤、分页参数和 `X-Total-Count`。普通管理员的审计视图只包含本人管理动作和普通用户目标，避免借审计日志枚举更高角色；超级管理员保留全局审计能力。

## D-026：页面原图不可变且处理结果按版本追加

- 状态：已确认
- 日期：2026-10-20
- 决策：`scan_pages` 保存不可变原图引用与当前活动结果元数据，`page_results` 以 `(page_id, version)` 唯一约束保存基础处理和手动旋转结果。Worker 成功始终完成作业，低质量只改变页面复核状态；手动旋转生成新版本，不能覆盖原图或既有版本。
- 影响：旧客户端继续读取 `processed_path` 和 `mime_type`，新客户端可查询历史版本、原图和结构化质量。账号合并同步迁移每个结果文件及所有者，账号删除显式清理结果记录。未来 AI 增强可追加新版本，但默认关闭且不能替换基础结果历史。

## D-027：作业提交必须同时校验状态与随机租约令牌

- 状态：已确认
- 日期：2026-10-20
- 决策：Worker 领取作业时生成不可预测的租约令牌；心跳、失败和结果提交都必须同时匹配当前令牌与处理状态。过期抢占生成新令牌，取消立即清空令牌。旧 PostgreSQL 作业枚举在 `0014` 转为有长度限制的字符串，后续新增阶段仍需迁移但不再重建数据库枚举类型。
- 影响：崩溃后恢复的旧 Worker、超时 Worker 和被取消 Worker 都不能覆盖新结果。基础结果文件与数据库版本/作业终态在同一事务边界收敛；少量数据库提交前留下的同版本孤儿文件可被安全覆盖。真实进程强杀、磁盘满和双 Worker 压力仍需 OPS 阶段在 staging 验证。

## D-028：基础 OCR 使用固定离线模型并绑定页面结果版本

- 状态：已确认
- 日期：2026-10-20
- 决策：基础 OCR 使用 `paddleocr==3.7.0`、`paddlepaddle==3.3.1` 和只读本地 PP-OCRv6 small 模型包；模型清单固定运行库/模型版本及全部文件 SHA-256。四方向结果在 Worker 内融合，OCR 数据绑定 `active_result_version`，项目建议名称与用户标题分离。
- 影响：生产禁止关闭本地 OCR 或在首次请求联网下载模型；模型升级必须更换内部版本并重跑固定集。手动旋转会把旧 OCR 标记为过期。自动测试证明适配和安全边界，不代表真实方向正确率达到 v1.4 的 `98%`，真实模型包、数据集、CPU 耗时与内存仍需人工门禁。

## D-029：导出请求冻结版本证据，多页 JPG 保持多制品

- 状态：已确认
- 日期：2026-10-20
- 决策：每次导出都保存页面顺序、活动结果版本和实际 OCR 版本快照。JPG 对每页生成独立制品，PDF 对选中页面生成单一制品；不把多页 JPG 隐式改成未在产品范围内声明的 ZIP。OCR 文本层只使用当前版本的结构化行框，无法证明对应关系时降级为纯图像 PDF。
- 影响：客户端可从同一导出响应获得有序制品列表，但文件内容下载由 `FILE-001` 增量提供。同步生成适合当前单机基线；超大项目的队列化、并发配额与内存门禁需结合目标服务器容量数据决定，不能用本地小样本宣称通过。

## D-030：鉴权与文件传输分离，删除采用持久化清理状态

- 状态：已确认
- 日期：2026-10-20
- 决策：API 始终负责资源鉴权、`404` 隐藏和审计；本地由应用处理 Range，Compose 生产基线通过 Nginx `internal` 位置发送文件。上传取消先持久化状态再回收分片，项目删除把规范化文件清单保存到 `project_deletions`，数据库资源删除后由 Worker 重试文件擦除。
- 影响：Nginx 不获得独立鉴权入口，文件系统短暂失败也不会丢失续接证据。降级不能恢复已删除项目；必须等待待清理队列为空。账号合并在存在待清理项目时拒绝，避免迁移与删除同时改写文件所有权。

## D-031：API 冻结使用当前快照与上一代客户端基线双门禁

- 状态：已确认
