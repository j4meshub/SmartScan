# 书籍页码、完整性与增量成册

本文说明 `BOOK-003` 的页码证据、缺页/重复页判断、人工决策、补扫和增量 PDF 边界。该能力用于降低漏扫与重复扫描风险，不把逻辑顺序伪装成印刷页码，也不覆盖任何原图。

## 证据模型

- Worker 只在页面顶部或底部的常见页码区域读取 OCR 候选，支持阿拉伯数字和规范罗马数字。多个分数接近但含义不同的候选标记为“不确定”，不会选一个猜测值。
- 页码标签、数值、数字类型、置信度、原因和内容指纹都绑定活动处理结果版本。旋转、裁切或滤镜产生新版本后，旧证据立即失效并等待重算。
- 没有识别到印刷页码的页面仍按项目内部页序成册。客户端只显示真实识别或用户补扫时声明的预期标签，绝不把内部页序展示为印刷页码。
- 内容指纹使用本地图像感知哈希，只用于发现高度相似页面。它不是原图替代品，也不上传到外部 AI。

## 完整性规则

系统按当前、未被替代的逻辑页动态计算问题，而不是保存容易过期的“缺页结果”：

- 相邻且同类型的可见页码存在小范围跳号时，逐页生成缺页问题；跨度过大时只提示不确定缺口，避免产生大量虚假页码。
- 相同页码且图像高度相似时标记疑似重复；相同页码但内容差异明显时标记页码冲突。
- 无相同页码但图像几乎一致时也标记疑似重复。
- 双页拆分只得到单侧、页码候选冲突、补扫预期页码不匹配、页面质量待复核或页码顺序倒退时均进入人工处理清单。
- 重新排序、编辑、单侧重拍、补扫或处理版本变化后，报告从当前证据重新生成，不沿用陈旧问题。

## 人工决策与原图保护

用户可对当前问题选择忽略、确认页面不存在、保留两页或排除重复页，也可重新打开既有决策。决策单独记录操作人、时间和问题键，不删除机器证据。

“排除重复页”只修改成册快照是否包含该逻辑页；页面、物理原图、派生源图和历史处理结果继续保留。重新打开决策会恢复该页。未授权和不存在的项目统一返回 `404`，跨用户补扫与成册失败写入审计。

## 补扫与增量 PDF

缺页补扫需要显式的插入位置和预期印刷页码标签。服务端保存新的不可变原图，顺延后续内部页序，并通过普通 Worker 流程重新提取页码、质量、OCR 和指纹。若实际证据与预期标签不一致，仍阻塞成册，不能用用户输入覆盖 OCR 事实。

成册前必须满足：至少包含一页、所有包含页已有活动处理结果、当前问题都已处理。服务端以有序页面 ID、结果版本、OCR 版本、质量档位和文本层开关生成稳定签名：

- 完全相同的快照重复提交会复用已就绪导出；
- 补扫、重排、编辑或质量选项变化会生成下一修订；
- 新修订记录上一导出 ID，形成可审计链；
- PDF 仍复用既有三档质量和可选 OCR 文本层，OCR 不可用时不伪造文本。

## 接口

- `GET /v1/projects/{project_id}/book-integrity`：读取当前动态报告。
- `PUT /v1/projects/{project_id}/book-integrity/decision`：保存决策或使用 `reopen` 重新打开。
- `POST /v1/projects/{project_id}/book-supplements`：上传补扫页并指定插入位置、预期页码。
- `POST /v1/projects/{project_id}/book-assemblies`：创建或复用版本化 PDF 成册结果。

H5、Android 和 iOS 均消费同一报告，显示印刷页码、阻塞问题与处理入口。Android 编译/Lint 和 iOS Simulator 编译测试以 GitHub Actions Runner 为准。

## 验收边界

自动化覆盖页码区域约束、罗马数字规范化、候选冲突、指纹距离、缺页补扫、重复排除/恢复、页码冲突、增量修订、IDOR、迁移和三端契约。以下仍是人工门禁：

- 至少 5 本书、1000 个逻辑页面和 300 次双页取景的授权固定数据集；
- 重复阻止率 `>=98%`，明显连续缺页检出率 `>=95%`；
- Android 企业微信环境与 iPhone 真机的连续扫描、补扫和成册流程；
- 大型书籍 PDF 的目标服务器耗时、内存和存储容量。

在这些门禁通过前，工作包状态为“等待人工验收”，不得把合成测试或 Simulator 结果描述成真实指标通过。
